| **La API carga sola una sincronización del catálogo aplicada por otro proceso** (un `catalog-sync.js` al lado de la API). Un cron de la API (`catalog-memory`, cada minuto, nunca en un CLI) compara la última sincronización aplicada de la base con la que tiene en memoria y, si es otra, la carga como al final de una sincronización propia. No lo hace mientras esta API sincroniza, porque en ese momento la base ya va adelante y la recarga viene al final. Si cargarla falla, queda el catálogo anterior y se reintenta al minuto siguiente. Mientras tanto, el aviso `catalog_memory` dice qué sincronización tiene cada uno, si el último intento falló y qué hacer («Sincronizar» o reiniciar). `system_status` suma `loadedSyncId` y `latestAppliedSyncId`. | Después de un `catalog-sync.js` había que reiniciar la máquina: hasta entonces las pantallas mostraban el catálogo viejo y cada importación de la colección daba `409 catalog_changed` (el bajo 4 de la revisión de #95). Cargarlo cuesta lo mismo que la recarga que ya hace la API después de una sincronización suya. |
