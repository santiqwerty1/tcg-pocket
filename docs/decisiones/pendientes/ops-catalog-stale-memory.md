| **La API carga sola una sincronización del catálogo aplicada por otro proceso** (un `catalog-sync.js` al lado de la API). Un cron de la API (`catalog-memory`, cada minuto, nunca en un CLI) compara la última sincronización aplicada de la base con la que tiene en memoria y, si es otra, la carga como al final de una sincronización propia. No lo hace mientras esta API sincroniza, porque en ese momento la base ya va adelante y la recarga viene al final. Si cargarla falla, queda el catálogo anterior y se reintenta al minuto siguiente. Mientras tanto, el aviso `catalog_memory` dice qué sincronización tiene cada uno, si el último intento falló y qué hacer (reiniciar la máquina). No sale mientras esta API sincroniza. Una carga lenta no arranca otra al minuto siguiente. Una sincronización cuya carga en memoria falla después del commit queda `applied` (antes quedaba `failed` con las tablas ya cambiadas), y el cron la carga después. Un catálogo aplicado sin cartas no vacía el de la memoria. `system_status` suma `loadedSyncId` y `latestAppliedSyncId`. | Después de un `catalog-sync.js` había que reiniciar la máquina: hasta entonces las pantallas mostraban el catálogo viejo y cada importación de la colección daba `409 catalog_changed` (el bajo 4 de la revisión de #95). Cargarlo cuesta lo mismo que la recarga que ya hace la API después de una sincronización suya. |
| **«Sincronizar» sin commit repite el último commit aplicado en la base,** no el de la memoria. Con él también se compara un commit pedido (más nuevo, igual o anterior). | Después de un `catalog-sync.js`, la memoria puede estar atrasada hasta un minuto, o más si la carga falla. Repetir su commit deshacía la sincronización del CLI sin pedir confirmación, porque contra sí mismo daba «igual» (autorrevisión de este PR). |
