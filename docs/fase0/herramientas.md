# auth

## Resumen
Ninguna de estas herramientas hace falta si tu cuenta muestra «Request headers» (static_headers) al agregar el conector: seguí con bearer `tcg_mcp_*` (0,5 día) y Claude Code con `--header`. Ese chequeo de 10 minutos sigue siendo lo primero (PLAN A6).
Si NO aparece, la forma más barata de sacar el riesgo «OAuth para el conector» no es escribir el AS (1–2 semanas) ni, en primera instancia, better-auth (2–4 días), sino usar un AS externo gratis y dejar nuestro Nest como resource server: PRM estático en `/.well-known/oauth-protected-resource` + guard que acepte `tcg_mcp_*` o un JWT verificado por JWKS con `iss`/`aud` configurables por env. Eso es **~1 día** con WorkOS AuthKit (más simple, 1M MAU, MFA/passkeys gratis, pero login separado en su pantalla de consentimiento) o **~1–2 días** con Descope (CIMD+DCR, Claude citado en docs, 2.000 consentimientos/mes gratis y BYOA para que el consentimiento use nuestro password+TOTP). Scalekit es técnicamente el mejor (BYOA limpio) pero su pricing de MCP Auth es contradictorio (Free vs add-on 99 US$/mes): vale 15 minutos crear la cuenta y ver si «MCP servers» está habilitado en Free antes de descartarlo.
Clerk: no (sin TOTP/passkeys en Free, UI y dominio propios obligatorios). Supabase Auth como AS: no (beta, sin scopes custom ni CIMD, consent UI a construir, pausa semanal; solo tendría sentido migrando toda la DB, ya descartado).
Ninguno conviene para reemplazar el login propio de la PWA (password+TOTP, ~300 líneas): para un usuario suman más dependencia que ahorro. Recomendación concreta para el PLAN: mantener el diseño del verificador pluggable, cambiar la estimación de M8-OAuth de «2–4 días (better-auth) / 1–2 semanas (a mano)» a «1–2 días con AS externo (Descope o WorkOS), better-auth como salida si no querés terceros», y agregar como riesgo el cambio de free tiers (mitigado por el guard JWKS genérico). Verificado con la doc de Claude (6/10/2026): CIMD se usa solo si el AS publica `client_id_metadata_document_supported: true` y `none` en `token_endpoint_auth_methods_supported`; si no, DCR; PKCE S256 siempre; callback `https://claude.ai/api/mcp/auth_callback`; 10 s de timeout; refresh rotado. Los cuatro vendors declaran DCR, así que el peor caso sigue funcionando.

## Descope (Agentic Identity Hub · MCP Servers / Inbound Apps) — veredicto: quizás
**Qué es:** CIAM completo (login, MFA, passkeys, tenants) con un producto específico «MCP Servers»: Descope actúa como Authorization Server OAuth 2.1 y nuestro NestJS queda como resource server. En este proyecto: reemplazaría el AS OAuth que el plan prevé escribir a mano o montar con better-auth (§2, §3.8). Verificado en docs (6/10/2026): registro de clientes **CIMD + DCR (RFC 7591) + pre-registro**, con toggles por servidor y recomendación explícita de habilitar CIMD y DCR; emite **JWT** con `aud` = URL del MCP server, validables con su **JWKS**; publica metadata RFC 8414; nosotros hospedamos el PRM (RFC 9728) en `<url>/.well-known/oauth-protected-resource`; pantalla de consentimiento con scopes descriptos; **menciona a Claude** como cliente (varios usuarios de Claude aparecen como un único cliente CIMD); «Bring Your Own Auth»: el *User Consent Flow* puede validar contra nuestro login (acción *External Authentication* → nuestro backend llama `externalauth/complete`, o *Generic HTTP Connector*) y hasta reutilizar nuestra cookie de sesión, aunque la UI de consentimiento sigue siendo hosted de Descope. Issuer en dominio de Descope o custom domain (incluido gratis). PKCE: Claude exige S256 y la doc de Descope no lo detalla (no verificado explícitamente; es obligatorio en OAuth 2.1).

**Precio:** **Free Forever 0 US$** (descope.com/pricing y descope.com/pricing.md, 6/10/2026): «7,500 MAUs», «10 Monthly Active Tenants», «3 SSO Connections», «1 Federated App (OIDC)», custom domain incluido, «All auth methods» (passkeys y authenticator apps incluidos), **«2,000 Monthly active consents (MACs)»** (métrica de Inbound Apps/MCP: 1 usuario que consiente 1 vez al mes = 1 MAC), «10,000 M2M exchanges». **Pro desde 249 US$/mes** (anual, 5,000 MAC), **Growth desde 799 US$/mes** (10,000 MAC). No encontré límite de cantidad de MCP servers por plan (no verificado). Para 1 usuario: 0 US$ con margen enorme.

**Encaje:** Es el candidato externo más completo para exactamente lo que falta en M8: CIMD + DCR + JWKS + Claude probado, gratis, sin custom domain obligatorio. Esfuerzo como AS **solo para el conector**: ~1 día (crear MCP server en dashboard con URL `/api/mcp`, scopes `mcp:read`/`mcp:write`, habilitar CIMD+DCR; en Nest: endpoint PRM estático + guard que acepte `tcg_mcp_*` o JWT verificado contra el JWKS de Descope con `iss`/`aud`); +1 día si querés BYOA para no tener una segunda contraseña (el flow redirige a nuestro `/login` password+TOTP y vuelve). **No** lo adoptaría para reemplazar la sesión de la PWA: Flows (builder low-code) + SDK + cookie de Descope son más piezas que las ~300 líneas propias para un usuario, y atan todo el acceso a un tercero. Queda como **primer plan B** si tu cuenta no muestra «Request headers».

**Riesgos:** - Salto de precio brutal (0 → 249 US$/mes) si cambian límites del Free (ya cambiaron el modelo a MAC en 2025).
- UI de consentimiento y login del flujo OAuth hosted por Descope (brandeable, no propia).
- Curva de Flows si usás BYOA; sin BYOA tendrías dos credenciales (la de la app y la de Descope).
- Lock-in mitigable: el guard de Nest debe ser un verificador JWT/JWKS genérico (issuer y audience por env) para poder cambiar de AS sin tocar las tools.
- Disponibilidad: el AS debe responder en <10 s desde el egress de Anthropic; es SaaS, debería cumplir.

## WorkOS + AuthKit (User Management + Connect) — veredicto: quizás
**Qué es:** WorkOS es la plataforma (SSO, Directory Sync, User Management); AuthKit es su caja de login (hosted o «host your own frontend» con las APIs headless de User Management). Para este proyecto importa **AuthKit como OAuth AS para MCP** (docs workos.com/docs/authkit/mcp, 6/10/2026): **CIMD** (agregado nov-2025, off por defecto, se habilita en Dashboard → Connect → Configuration) y **DCR** (RFC 7591, toggle «para compatibilidad»); `code_challenge_methods_supported: ["S256"]`; metadata RFC 8414 en `https://<authkit_domain>/.well-known/oauth-authorization-server`; **Resource Indicators (RFC 8707)**: hay que registrar la URL del endpoint MCP en el dashboard y el token sale con `aud` = esa URL; nuestro Nest verifica el **JWT con `jose` contra `https://<authkit_domain>/oauth2/jwks`** (issuer + audience) y hospeda el PRM. Incluye pantalla de consentimiento hosted. La doc de MCP no nombra a Claude (sí sus posts de blog). Custom domain **opcional**, pago.

**Precio:** **workos.com/pricing (6/10/2026)**: AuthKit/User Management «First 1M MAUs» gratis incluyendo «email + password, social login, passkeys, MFA, magic auth, enterprise SSO»; luego «$2,500/mo» por cada 1M MAU extra. SSO/Directory Sync «$125/ea» por conexión (no nos aplica). **Custom Domain «$99/mo»** (no obligatorio: docs/custom-domains dice que en producción «you have the option»). Connect (OAuth provider/MCP) no aparece como línea de precio: lo tomo como incluido, **no verificado explícitamente**. Para 1 usuario: 0 US$.

**Encaje:** El AS externo **más simple y más barato de operar**: sin tope de consentimientos, MFA (TOTP) y passkeys gratis, sin custom domain. Esfuerzo como AS del conector: **~1 día** (cuenta, habilitar CIMD y DCR, registrar `https://<dominio>/api/mcp` como Resource Indicator, PRM + guard JWKS en Nest, prueba con MCP Inspector y conector real). Costo de diseño: **no tiene BYOA para el flujo MCP**: la pantalla de consentimiento te pide loguearte en AuthKit, así que tendrías una identidad en WorkOS (email+password+TOTP/passkey) distinta de la de la PWA, usada solo cuando Claude pide consentimiento (una vez, luego refresh rotado). Reemplazar también la sesión de la PWA con AuthKit (hosted o headless) es viable pero cambia tu middleware «nada sin cookie» por sesiones selladas de WorkOS: para un usuario no ahorra complejidad neta y suma dependencia. Lo pondría como **plan B empatado con Descope**: WorkOS si aceptás dos logins y querés cero configuración; Descope si querés un solo login vía BYOA.

**Riesgos:** - Dos conjuntos de credenciales (app + WorkOS) salvo que migres toda la auth a AuthKit.
- Connect/CIMD son features recientes: verificar al crear la cuenta que el metadata publique `client_id_metadata_document_supported: true` y `none` en `token_endpoint_auth_methods_supported` (si no, Claude cae a DCR, que WorkOS también soporta).
- Dominio por defecto de AuthKit: no pude verificar el patrón exacto en la doc (presumiblemente `*.authkit.app`).
- Lock-in bajo si el guard es JWKS genérico; el free tier de 1M MAU es estable desde 2024 pero puede cambiar.

## Scalekit (Auth for MCP) — veredicto: quizás
**Qué es:** Plataforma B2B (SSO/SCIM, «SaaSKit» full-stack, AgentKit) con un producto **«Auth for MCP»**: AS OAuth 2.1 drop-in para MCP servers. Docs (docs.scalekit.com/guides/mcp/*, 6/10/2026): registrar el MCP server en dashboard, habilitar **DCR y CIMD**, resource identifier = URL del server (va en `aud`), PRM en `.well-known/oauth-protected-resource` copiado del dashboard, validación de **JWT RS256** con `validateToken()` del SDK Node o JWKS sin llamada en vivo, scopes por tool, consentimiento y vida de tokens configurables; cita RFC 8414/7591/9728 y OAuth 2.1 con PKCE; ejemplos con Claude Desktop/Cursor/VS Code. **Bring Your Own Auth** (docs.scalekit.com/mcp/auth-methods/custom-auth): Scalekit redirige a nuestro `/login` con `login_request_id` + `state`, nuestro backend autentica (password+TOTP propio) y llama `updateLoginUserDetails()` con `sub`/`email`, redirigimos de vuelta y Scalekit hace consentimiento y tokens. Custom domain opcional.

**Precio:** **Contradictorio, marcar como no resuelto.** scalekit.com/pricing/auth-for-saas (6/10/2026): SaaSKit **Free 0 US$** «25,000 MAUs (hard cap)», «25 organizations», «1 SSO & 1 SCIM», branding de Scalekit; **Growth 99 US$/mes** incluye «MCP Auth with your branding»; plan **BYOA Free 0 US$** (1 SSO + 1 SCIM) y BYOA Growth 99 US$/mes con «Add MCP auth on top of your current stack + Add-on: $99/mo». La landing scalekit.com/mcp-auth dice «free plan available» y terceros/snippets hablan de «MCP Auth free up to 1M users and agents» (página pricing-v6 devuelve 404). Custom domain & branding: add-on 99 US$/mes. **No pude confirmar que Auth for MCP sea gratis en el Free actual**; hay que verlo en el dashboard al crear la cuenta.

**Encaje:** Técnicamente el mejor encaje: BYOA documentado = un solo login (el nuestro), Scalekit solo hace OAuth/consentimiento/JWT, y el SDK Node valida tokens en Nest. Esfuerzo: **~1–2 días** (dashboard + PRM + guard JWT + endpoint `/login` que entienda `login_request_id` y llame al SDK). Pero el veredicto depende del precio: si MCP Auth exige Growth o el add-on de 99 US$/mes, es **no** (supera 20× el costo de toda la infra). Si al crear la cuenta gratis aparece «MCP servers» utilizable sin add-on, pasa a ser mi primera opción por delante de Descope. Acción concreta: 15 minutos para crear cuenta y mirar si el menú MCP está habilitado en Free.

**Riesgos:** - Precio ambiguo/cambiante (tres páginas de pricing distintas en el sitio; /pricing hoy muestra AgentKit).
- Empresa chica y producto en rotación (AgentKit, Agent Gateway en early access): riesgo de que el Free cambie.
- Branding de Scalekit en la pantalla de consentimiento salvo add-on.
- La misma mitigación: guard JWKS genérico para poder migrar a Descope/WorkOS/better-auth.

## Clerk — veredicto: no
**Qué es:** Auth de producto (componentes prebuilt, sesiones, orgs) que además es **OAuth provider**: DCR (toggle en OAuth applications → Settings → «Client onboarding»), **CIMD GA desde 17/9/2026** («Publish CIMD support», PKCE S256 obligatorio para CIMD), metadata de AS «out of the box» (changelog 13/6/2025). Para MCP ofrece `@clerk/mcp-tools` (Express, Hono, Next): `mcpAuthClerk` verifica el bearer, `protectedResourceHandlerClerk` sirve el PRM en `/.well-known/oauth-protected-resource/mcp` y `authServerMetadataHandlerClerk` proxya el metadata para clientes viejos. Los access tokens OAuth pueden ser JWT u **opacos**; la verificación oficial es por SDK (`acceptsToken`) o por el endpoint REST `/oauth_applications/access_tokens/verify` con tu secret key (introspección: una llamada a Clerk por request). Un instance de **producción exige dominio propio con registros DNS** (docs deployment/production). No hay BYOA: el usuario se loguea con su cuenta Clerk en la UI de Clerk.

**Precio:** **clerk.com/pricing (6/10/2026)**: Free «50,000 MRU limit per app», «Unlimited applications», custom domain, «Up to 3» social logins, **sin passkeys ni MFA** («No passkeys or biometric sign-in», «No multifactor authentication»), logs 1 día. **Pro «$25/mo» (20 US$ anual)**: MFA, passkeys, 1 SSO, quitar branding. Add-ons B2B/Admin 100 US$/mes. Un snippet de búsqueda dice que el uso de machine tokens es «free during the public beta… subject to pricing once GA»: **no lo encontré en la página de docs, no verificado**.

**Encaje:** El plan ya lo descartó (hosting-mcp.md §4) y la verificación lo confirma: el **Free no incluye TOTP ni passkeys**, que es justo lo que el brief pide para el login, así que reemplazar la sesión propia costaría 25 US$/mes (>6× la infra). Como AS solo para el conector funciona (CIMD+DCR+PRM listos y Express encaja en Nest), pero obliga a una identidad Clerk con UI de Clerk, producción con DNS propio y verificación por introspección (dependencia en cada request MCP). No aporta nada que Descope/WorkOS no den gratis con MFA incluida.

**Riesgos:** - MFA/passkeys solo en Pro; posible cobro futuro de machine tokens (no verificado).
- Tokens opacos → introspección con secret key en cada request, o configurar JWT; latencia y dependencia.
- Producción requiere dominio propio + hasta 48 h de propagación DNS.
- Lock-in alto de UI (componentes Clerk) si lo usás para la PWA.

## Supabase Auth (OAuth 2.1 Server) · punto de comparación — veredicto: no
**Qué es:** Supabase Auth puede actuar como **OAuth 2.1 / OIDC server** («Sign in with your app», MCP). Docs (supabase.com/docs/guides/auth/oauth-server y /mcp-authentication, features/oauth2-1-server, 6/10/2026): estado **«Public Beta»** (changelog apuntaba a GA Q4-2025; la página de features sigue en beta); authorization code + **PKCE obligatorio**, refresh tokens, **DCR** con toggle en Authentication → OAuth Server (advierte que «any MCP client» podrá registrarse), metadata en `https://<ref>.supabase.co/.well-known/oauth-authorization-server/auth/v1`, **JWKS** para validar JWT; **hay que construir la pantalla de autorización/consentimiento** uno mismo (hay un bloque UI «OAuth Consent» y helpers `withOAuthProtectedResource()` / `withSupabase({auth:'user'})` para el MCP server); scopes solo `openid email profile phone` (los tokens tienen **todos los privilegios del usuario**, la autorización se delega a RLS); **CIMD no aparece en ninguna doc** (Claude caería a DCR, que sí existe). Custom domain no obligatorio (issuer = dominio del proyecto).

**Precio:** **supabase.com/pricing (6/10/2026)**: Free «50,000» MAU, **MFA TOTP «Included»**, phone MFA no, custom domain «$10 per domain per month» solo Pro+, DB 500 MB, **proyecto suspendido «After 1 week of inactivity»**, Pro «from $25/month». El OAuth server no tiene cargo aparte: cuenta contra MAU.

**Encaje:** Como **AS externo con Neon** no tiene sentido: sería un segundo backend de identidad con su propio Postgres, pantalla de consentimiento a escribir por nosotros (parte del trabajo que queríamos evitar), sin scopes propios (`mcp:read`/`mcp:write` imposibles), beta pública y riesgo de pausa semanal que rompería refresh tokens si Claude queda un tiempo sin usarse. Solo tendría lógica si el plan cambiara **toda la DB a Supabase** (500 MB vs 1 GB de Neon, sin backups en Free), opción que el PLAN §2 ya descartó. Esfuerzo si igual se hiciera: 2–3 días (comparable a better-auth, con más limitaciones).

**Riesgos:** - Beta sin fecha de GA cumplida; sin scopes custom; sin CIMD.
- Pausa tras 7 días de inactividad en Free (habría que mantenerlo vivo).
- Duplica base de datos/identidad frente a Neon + sesión propia.

# data

## Resumen
De las tres, solo **Supabase** mejora el plan: reemplazá **Neon Free por Supabase Free** (Postgres estándar, mismas extensiones, misma región que Fly, sin tope de CU-h ni scale-to-zero: el polling del worker deja de ser un riesgo y pasa a ser lo que evita la pausa semanal), mandá los **replays y el export diario a Supabase Storage** (1 GB, S3) en vez de a Postgres/R2, y evaluá **pg_cron + pg_net como tick externo** para correr Fly con `min_machines_running = 0`. Costo: 0 US$ a cambio de 500 MB (vs 1 GB) y sin PITR (vs 6 h), cubierto con Storage + export. **Supabase Auth + OAuth 2.1 Server** queda «quizás» y depende de A6: si no tenés «Request headers», es la vía más corta (~1 día) para el AS del conector MCP, pero está en beta y no la probé con claude.ai. **PlanetScale: no** (sin free tier, 5 US$/mes mínimo + tarjeta; no aporta nada que Supabase no dé gratis). **Turso: no** (SQLite, sin `SKIP LOCKED`/pg_trgm/unaccent, Prisma Migrate no soportado, y acaba de ser comprada por Supabase).

## PlanetScale (Postgres) — veredicto: no
**Qué es:** DBaaS de PlanetScale, históricamente MySQL/Vitess; desde 2025 ofrece Postgres gestionado (single-node o HA, con branching, PgBouncer integrado, backups cada 12 h, extensiones). En este proyecto reemplazaría a Neon Free como la base Postgres de `apps/api` (Prisma 7 + `@prisma/adapter-pg`, puerto directo 5432 o PgBouncer 6432).

**Precio:** **No hay free tier** (verificado 6/10/2026): «PlanetScale does not offer a free plan, previously known as the 'Developer' or 'Hobby' plan» (planetscale.com/docs/concepts/planetscale-plans). Postgres mínimo: **PS-5 single-node (non-HA) 5 US$/mes**, 1/16 vCPU, 512 MiB RAM, arm64 o x86 (planetscale.com/pricing, 6/10/2026); HA 3 nodos desde 15 US$. Storage de red cobrado aparte (el doc de planes habla de «10 GB included» para Base, no pude confirmar si aplica al SKU de 5 US$: **sin verificar**). Tarjeta: «All plans require that your organization has a valid payment method on file» (planetscale.com/docs/concepts/billing). Backups: «automatic scheduled backups that run every 12 hours…There are no additional charges», retención por defecto 2 días, PITR por WAL hasta 5 min antes del presente, storage de backup incluido 2× el disco (planetscale.com/docs/postgres/backups). Regiones: `us-east` (us-east-1) y `aws-sa-east-1` (São Paulo) para Postgres (planetscale.com/docs/concepts/regions). Extensiones: pg_trgm 1.6 y unaccent 1.1 soportadas sin superusuario (planetscale.com/docs/postgres/extensions). Pooling: PgBouncer en 6432, directo en 5432, «Both connection types will disconnect when your database restarts» (planetscale.com/docs/postgres/tutorials/planetscale-postgres-prisma).

**Encaje:** Es Postgres «de verdad» (pg_trgm, unaccent, índices únicos parciales, bytea, `SKIP LOCKED`: todo estándar) y siempre encendido, o sea elimina de un saque el riesgo «Neon 100 CU-h con el worker cada 30 s» y el cold start. Pero **cuesta 5 US$/mes mínimo**, más que el propio Fly (3,69), y pide tarjeta: duplica el costo total del proyecto para un solo usuario cuando Supabase Free resuelve exactamente lo mismo (Postgres always-on, sin tope de horas) a 0 US$. PITR de 2 días es mejor que las 6 h de Neon, pero no justifica 60 US$/año. Lock-in nulo (Postgres plano), compatibilidad Prisma 7 vía `@prisma/adapter-pg` sin nada especial (el tutorial oficial usa `prisma init` genérico; no menciona adapters: **sin verificar con Prisma 7 específicamente**). No reemplaza ni agrega nada que no den Neon o Supabase gratis.

**Riesgos:** - 1/16 vCPU y 512 MiB: compute muy chico; probablemente peor que Neon 0,25 CU para el diff de 4.317 filas (no medido).
- Single-node sin HA: una caída = app caída; para un usuario es aceptable pero pagás igual.
- Si algún día querés ir a 0 US$, hay que migrar (trivial con `pg_dump`, pero es trabajo).
- Storage incluido en el SKU de 5 US$ **sin verificar**: podría haber costo extra por GB.

## Turso — veredicto: no
**Qué es:** Base de datos SQLite gestionada (Turso Database, reescritura de SQLite con MVCC y sync, más libSQL), con muchas DBs baratas, embedded replicas y PITR. En este proyecto sería el reemplazo de Neon/Postgres por SQLite remoto, accedido desde Nest con `@prisma/adapter-libsql`.

**Precio:** Free (verificado turso.tech/pricing, 6/10/2026): «Start free, no credit card required»; **100 DBs, 5 GB storage, 500 M rows read/mes, 10 M rows written/mes, 3 GB syncs/mes, PITR 1 día**, soporte comunitario. Developer 4,99 US$/mes (9 GB, 2,5 B reads, 25 M writes, PITR 10 días), Scaler 24,92 US$/mes. Regiones: Free en ubicaciones Fly (incluye `gru` São Paulo e `iad`); el Developer «is also only available on AWS» (turso.tech/blog/turso-cloud-debuts-the-new-developer-plan, 19/3/2025; la página docs.turso.tech/cloud-providers redirigió al home: **parcialmente verificado**). Prisma: `@prisma/adapter-libsql` documentado para Prisma 7 (prisma.io/docs/orm/overview/databases/turso), pero «Prisma Migrate and Introspection workflows are currently not supported when working with Turso» (docs.turso.tech/sdk/ts/orm/prisma): migraciones = `prisma migrate diff` contra SQLite local + CLI de Turso. **Adquisición: Supabase anunció la compra de Turso en octubre de 2026** (siliconangle, pulse2, runtimewire; el home de turso.tech no lo menciona); «Turso will continue operating its existing platform».

**Encaje:** Es SQLite, no Postgres: se pierden pg_trgm, unaccent y sobre todo `UPDATE … SKIP LOCKED … RETURNING` del claim atómico del worker (§3.7), el `bytea` pasa a BLOB y las migraciones Prisma quedan a mano. Todo el PLAN está escrito sobre Postgres + Prisma 7 y vos ya conocés Postgres; Turso obligaría a reescribir modelo, búsqueda (habría que hacer unaccent/trigram en TypeScript) y el flujo de migraciones. Los límites del free sobran (86 k polls/mes ≈ 0,02 % de las lecturas) y 5 GB > 1 GB de Neon, pero eso no compensa. Encima la adquisición por Supabase deja el roadmap de Turso Cloud en duda para un proyecto de 8–9 semanas que recién arranca. Solo tendría sentido en la opción C (Cloudflare/SQLite), que ya descartaste.

**Riesgos:** - Incertidumbre de producto post-adquisición (precios, regiones Fly del Free, deprecaciones).
- Prisma Migrate no soportado: cada cambio de schema es un paso manual.
- Embedded replicas (lo único que agregaría valor para el worker offline) exigen filesystem y no abren la DB local mientras sincroniza; soporte Windows **sin verificar**.
- Sin `SKIP LOCKED`/`FOR UPDATE`: hay que rediseñar el lease del worker con transacciones serializadas.

## Supabase — veredicto: sí
**Qué es:** Postgres gestionado (AWS) + Auth (password, TOTP, passkeys experimental, servidor OAuth 2.1 en beta) + Storage (S3-compatible) + Edge Functions (Deno) + Cron (pg_cron + pg_net). En este proyecto: (a) reemplaza a **Neon Free** como la Postgres de `apps/api`, siempre encendida; (b) Storage reemplaza «replays comprimidos en Postgres» y el eventual R2; (c) pg_cron + pg_net puede disparar el tick del scheduler de Fly (alternativa a `min_machines_running = 1` o GitHub Actions); (d) opcional: Auth + OAuth 2.1 Server como Authorization Server del conector MCP de Claude, en lugar de better-auth o un AS a mano.

**Precio:** Free (supabase.com/pricing, 6/10/2026): **0 US$**, «500 MB database size (Shared CPU • 500 MB RAM)» (compute Nano: 60 conexiones directas / 200 por pooler, supabase.com/docs/guides/platform/compute-and-disk), «1 GB file storage», «5 GB egress» + «5 GB cached egress», «50,000 monthly active users», «500,000 included» invocaciones de Edge Functions, «Limit of 2 active projects», backups «Not included», branching «Not included», «Basic Multi-Factor Auth» incluido (TOTP), MFA por teléfono no (75 US$/mes en Pro). **«Free projects are paused after 1 week of inactivity»**; detalle (supabase.com/docs/guides/platform/free-project-pausing): «a few user requests to the database each day over the previous week is enough to keep the project from being paused», aviso por mail ~1 semana antes, «1-year window to restore»; los pagos no se pausan. Pro 25 US$/mes (8 GB disco, 100 GB storage, backups 7 días, Micro incluido). Archivo máximo en Storage Free: «the limit can't exceed 50 MB» (docs/guides/storage/uploads/file-limits). Regiones: `sa-east-1` São Paulo, `us-east-1`, `us-east-2` (docs/guides/platform/regions). Tarjeta: la doc oficial no lo dice; fuentes de terceros dicen «no credit card required» (**sin verificar en doc oficial**). Exceso de cuota en Free: «If you continue to exceed the limits, service restrictions will apply» (pausa/solo lectura) (docs/guides/platform/billing-faq). OAuth 2.1 Server: «in beta and available on all Supabase plans. It has no separate charge» (docs/guides/auth/oauth-server/getting-started). Passkeys: «Passkey support is experimental. The API may change without notice», supabase-js ≥ 2.105.0 (docs/guides/auth/passkeys; beta anunciada en changelog 46458, mayo 2026). Cron: «anywhere from every second to once a year», recomiendan ≤ 8 jobs concurrentes y ≤ 10 min por job (docs/guides/cron); pg_net llama a cualquier URL externa, asíncrono, timeout por defecto 2000 ms, respuestas guardadas 6 h (docs/guides/database/extensions/pg_net). Prisma: Supavisor sesión 5432 (IPv4 en todos los planes) o transacción 6543 con `pgbouncer=true` + `DIRECT_URL`; conexión directa solo IPv6 o con add-on IPv4 (docs/guides/database/connecting-to-postgres; docs/guides/database/prisma); la guía de Prisma usa `@prisma/adapter-pg` pero está escrita para v6 (**Prisma 7 no documentado explícitamente**, pero el adapter es el mismo que ya elegiste). Extensiones: pg_trgm («create extension if not exists pg_trgm», índice de docs de Supabase), unaccent soportado según listados de terceros (**no abrí una página oficial de Supabase para unaccent**), pg_cron y pg_net verificados.

**Encaje:** **Como reemplazo de Neon: sí.** Neon Free te da 1 GB y 6 h de PITR pero con **100 CU-h/mes y scale-to-zero fijo a 5 min**, y el propio PLAN (§6, fila Neon) admite que el worker cada 30 s la mantiene despierta (180 CU-h) y obliga al truco de «cola vacía en memoria» y a cuidar que el AS OAuth responda en < 10 s con la DB fría. Supabase Free no tiene tope de cómputo ni sleep: el polling del worker y el cron diario de Limitless son exactamente la actividad que evita la pausa semanal, así que el único «riesgo» de Supabase se autocancela y desaparecen dos filas de riesgos del plan. Es Postgres estándar (pg_trgm, unaccent, índices parciales, bytea, `SKIP LOCKED`), misma región que Fly (`gru` ↔ `sa-east-1`, o `iad` ↔ `us-east-1`), `@prisma/adapter-pg` sin cambios (usá el pooler en modo sesión 5432, que es IPv4 y no necesita `pgbouncer=true`; conexión directa solo si Fly sale por IPv6, **sin verificar**). Contras: 500 MB vs 1 GB y sin PITR: por eso los replays van a **Supabase Storage desde el día 1** (1 GB, archivos ≤ 50 MB, API S3; reemplaza «replays en Postgres» y pospone R2 hasta pasar ~1 GB) y el export diario ya planeado (§3.9) se vuelve el backup real (guardalo también en Storage; subilo a 2 por día). **pg_cron + pg_net: quizás.** Un `net.http_post` cada 15 min a `/api/internal/tick` de Fly (con secreto) despierta la máquina si está auto-suspendida y dispara scheduler/backfill/backup: permitiría `min_machines_running = 0` (~1–2 US$/mes en vez de 3,69) sin GitHub Actions; con la PC encendida el long-poll del worker ya la mantiene despierta. **Auth + OAuth 2.1 Server: quizás, atado a A6.** Si tu cuenta muestra «Request headers», seguí con login a mano y bearer estático y no toques Supabase Auth. Si no, Supabase es el AS OAuth más barato que encontré: beta, gratis, PKCE, refresh tokens, JWT con `client_id`, discovery en `https://<ref>.supabase.co/.well-known/oauth-authorization-server/auth/v1`, DCR activable (Claude cae a DCR cuando no hay CIMD) y vos solo escribís la pantalla de consentimiento (`getAuthorizationDetails`/`approveAuthorization`) + PRM en Nest (`WWW-Authenticate` → AS de Supabase) + verificación JWKS del JWT en el guard MCP: ~1 día contra 2–4 con better-auth o 1–2 semanas a mano. Implica tener tu usuario en Supabase Auth (email + password + TOTP incluidos en Free), con lo cual conviene mover también el login de la PWA ahí y borrar las ~300 líneas a mano (la sesión de Supabase tiene que llegar en cookie para el middleware «nada se sirve sin autenticar»: `@supabase/ssr` o canjear el JWT por tu cookie `__Host-session`). Passkeys: experimental, no contar con ellas. Edge Functions: no las uses (Deno; todo vive en Nest).

**Riesgos:** - 500 MB de DB (Neon 1 GB): obliga a sacar replays y JSON crudo de Limitless de Postgres; los 12 k listados de torneos entran, pero medí al terminar Fase 5.
- Sin PITR ni backups en Free (Neon: 6 h): el export propio es la única red; si se corrompe algo entre exports, se pierde.
- Pausa a los 7 días: si Fly y la PC están apagados > 1 semana (vacaciones) se pausa; restaurar es un clic y los datos no se pierden (1 año), pero el conector de Claude queda caído hasta que lo hagas.
- Nano = CPU compartida 0,5 GB: suficiente para un usuario, pero no medido contra el diff del catálogo.
- Egress 5 GB/mes (R2 ilimitado): descargar muchos replays desde el celu lo come; bajo para este uso pero vigilarlo.
- OAuth 2.1 Server está en **beta**, no documenta CIMD ni `resource` (RFC 8707) ni lo probé contra claude.ai: validar con MCP Inspector + conector real antes de cerrar M8. DCR abierto deja que cualquier cliente se registre (el consentimiento sigue siendo tuyo; revisá clientes registrados). Redirect URIs exactas sin comodines: Claude Code con loopback de puerto dinámico puede no pasar por este AS (usá `--header` ahí).
- Dos proyectos activos por cuenta Free y «service restrictions» si excedés cuota.
- Lock-in moderado si adoptás Auth/Storage (la DB es Postgres plano y el export cubre los datos).
- Tarjeta y disponibilidad de la API S3 en Free: **sin verificar en doc oficial**.

## Sentry — veredicto: quizás
**Qué es:** Plataforma de observabilidad (errores con stack trace agrupado, tracing, session replay, logs, cron/uptime monitors). En este proyecto instrumentaría los tres procesos Node/JS: `apps/api` (NestJS en Fly) con `@sentry/nestjs`, `apps/web` (React/Vite PWA) con `@sentry/react` + plugin de Vite para source maps, y `apps/worker` (Node 24 en tu PC Windows) con `@sentry/node`. Además: 1 cron monitor (p. ej. el backup diario o el sync de Limitless cada 6 h) y 1 uptime monitor sobre `/healthz` (verifica que la máquina Fly con `min_machines_running = 1` esté viva).

**Precio:** **Developer (gratis), verificado en https://sentry.io/pricing/ el 6/10/2026:** US$ 0; «Limited to one user»; 5k errors/mes; 5M spans/mes; 50 replays/mes; 1 GB attachments; 5 GB logs; 1 cron monitor; 1 uptime monitor; proyectos ilimitados; retención «30-day lookback»; «Alerts and notifications via email» solamente; «MCP access» incluido; Seer (IA) requiere suscripción aparte; profiling solo con pay-as-you-go. Integraciones de terceros (GitHub/Slack) figuran como no incluidas en Developer según la comparativa de pricing; la doc de la integración GitHub (docs.sentry.io/organization/integrations/source-code-mgmt/github/) solo restringe explícitamente *issue sync* y *manual issue management* a Team+ — **ambiguo, no pude confirmar si el linking básico de stack traces funciona en Developer**. Team: US$ 26/mes (anual); Business: US$ 80/mes (anual).

SDKs (docs.sentry.io, 6/10/2026): `@sentry/nestjs` (Node ≥ 20.19; `instrument.ts` + `SentryModule.forRoot()` + `SentryGlobalFilter`; errores, tracing, logs, métricas), `@sentry/react` (React 19 vía `reactErrorHandler`, React Router v6/v7, Session Replay, source maps con `npx @sentry/wizard -i sourcemaps` para Vite), `@sentry/node` (Node ≥ 20.19, `node --import ./instrument.js`). Ninguna doc menciona limitaciones en Windows ni en PWA/service worker.

**Encaje:** **Lo que agrega sobre `fly logs`:** (1) errores del **PWA en el celular**, que hoy no verías de ningún modo (un `TypeError` en la hoja de «cargar partida» en Android no llega a Fly); con source maps subidos desde CI el stack apunta a tu TS. (2) `unhandledRejection` y panics del motor reportados por el **worker en tu PC**, aunque la API esté sana. (3) Agrupación/dedup de errores con contexto (release = commit, `engineRev`, chunk id) y 30 días de historial; `fly logs` es un stream en vivo y la retención prolongada exige un log drain [retención de logs de Fly no reverificada hoy]. (4) Cron monitor gratis para «el backup diario corrió» y uptime monitor para «la máquina sigue encendida» — justo los dos modos de falla silenciosa del plan (§6: Fly suspendida congela el scheduler). **No reemplaza nada** del plan; se suma. Compatibilidad: Fly/Neon/Windows sin problema (SDKs puros de Node; el browser habla directo con sentry.io, no toca el requisito «nada se sirve sin autenticar»). Costo 0 con un uso que para un usuario será de decenas de eventos/mes (5k errores es inalcanzable). Lock-in bajo (se quita borrando `instrument.ts`). Complejidad: ~1 h de setup; medio día si querés source maps en CI (token `SENTRY_AUTH_TOKEN` en Actions). **Mi recomendación:** no en Fase 1; agregarlo en Fase 2–3 cuando exista la PWA y el worker, que es donde aporta; antes alcanza con `fly logs` y pino.

**Riesgos:** - Plan Developer = **1 usuario y alertas solo por email**; sin GitHub/Slack (ambiguo para linking de código). Suficiente para vos, pero no esperes issues de GitHub creadas desde Sentry.
- Retención 30 días: si querés historial de errores de meses, no lo da.
- Session Replay (50/mes) y tracing son overkill para un usuario; dejar `tracesSampleRate` bajo o 0 y replay solo en error, para no generar ruido ni consumir ancho de banda del celular.
- Sube datos (URLs, stack, user-agent) a un tercero en EE. UU.; no hay PII real en esta app, pero conviene `sendDefaultPii: false` y filtrar el bearer de los headers (`beforeSend`).
- `@sentry/nestjs` usa OpenTelemetry por debajo e instrumenta `pg`/Prisma; agrega arranque y memoria en una máquina de 512 MB — medir, o desactivar integraciones automáticas de tracing.
- Dependencia de versiones: SDK v10+ requiere Node ≥ 20.19 (tenés 24, OK).

Sin límite de concurrencia y **1 minuto Windows 2vCPU = 2 minutos x64** [esto último proviene del extracto de búsqueda de docs.blacksmith.sh/runners/pricing; la página devolvió 404 al fetch directo — **no verificado de primera mano**]. **Windows:** sí existe, `blacksmith-{2,4,8,16,32}vcpu-windows-2025` (2 vCPU = 7 GB RAM, 130 GB disco), estado **«Windows Server 2025 (Public Beta)»**, imagen basada en la oficial de GitHub «with some exclusions»; sin contenedores Linux en Windows (docs.blacksmith.sh/runners/config, 6/10/2026). **Restricción clave (docs.blacksmith.sh/introduction/quickstart, 6/10/2026):** «Blacksmith is limited to GitHub organizations and not available for personal repositories.» Repos privados: sí, vía GitHub App instalada por repo (permisos Actions/Contents/Workflows read&write).

**Encaje:** **No cambia la matemática de minutos del proyecto.** El build del motor corre «solo al cambiar el `rev`» (§6) con caché de `~/.cargo` y `target`: una compilación fría de deckgym + engine-cli en Windows cuesta del orden de 10–20 min reales (estimación, no medida) → 20–40 minutos incluidos con el 2×; con caché, mucho menos; a 2–4 builds/mes son < 200 de los 2,000 minutos. Tests TS + imagen Docker en Linux suman quizás otros 100–300. Sobra margen. **Blacksmith además exige una organización de GitHub** (tu repo privado personal no califica; crear una org gratis es posible pero agrega cuenta, app y cambio de `runs-on` para ahorrar nada). Su Windows está en **beta pública** y consume minutos al doble, igual que GitHub. Lo único que mejoraría es velocidad (y la caché Rust de ~1 GB se baja más rápido), irrelevante para un build esporádico. **Cross-compilar desde Linux** (para evitar Windows del todo) es viable: deckgym parece Rust puro (rayon, serde, indicatif; sin C) → `x86_64-pc-windows-gnu` con `mingw-w64` de Ubuntu, o `cargo-xwin` para `x86_64-pc-windows-msvc` (descarga CRT/SDK de Microsoft, hay que aceptar su licencia; requiere clang + lld). Reduciría el costo a 1× y aceleraría, pero el binario no se probaría en Windows real en CI (sin Wine no hay smoke test); con 2,000 minutos libres no vale la complejidad. Si algún día el build se vuelve frecuente (p. ej. CI por PR del motor), el primer paso barato es cross-compile en `ubuntu-latest`, no Blacksmith.

- Windows runners en beta pública: posible inestabilidad, imagen «con exclusiones» respecto de la oficial (toolchain MSVC presente según la doc, pero no verifiqué la lista exacta).
- Minutos Windows a 2× (dato de extracto, página 404 al verificar).
- Otro proveedor con permisos read&write sobre Actions/Contents/Workflows de un repo que publica un `.exe` que el worker descarga y ejecuta: amplía la superficie de supply chain sin necesidad.
- Caché «25 GB por repo por semana»: suficiente para `target/` de Rust, pero es semanal, no mensual.

## CodeRabbit — veredicto: no
**Qué es:** Revisor de código con IA que comenta PRs en GitHub/GitLab (resumen/walkthrough, comentarios línea a línea, chat en el PR), con extensión VS Code y CLI. En este proyecto revisaría los PRs del monorepo (TS) y del crate `engine-cli` (Rust) — es decir, revisaría código que Claude Code acaba de escribir.

**Precio:** **Verificado en https://docs.coderabbit.ai/management/plans y https://www.coderabbit.ai/pricing el 6/10/2026:** **Free:** «Unlimited public and private repositories, no credit card required»; **«PR summarization only; code reviews are available through the VS Code extension and CLI»**; límites por desarrollador/hora: 1 PR review (solo resumen), 3 IDE reviews, 3 CLI reviews, 150 archivos por review, sin chat; «New organizations start with a 14-day Advanced trial». **Open Source:** repos públicos con features Team gratis. **Essentials** (ex Pro): US$ 24/dev/mes anual o US$ 30 mensual (5 PR reviews/h, 50 chats/h, 5 MCP connections). **Team:** US$ 48/mes anual o US$ 60 mensual. **Advanced:** US$ 72 anual / US$ 90 mensual. Enterprise: contacto. Trial 14 días sin tarjeta.

**Encaje:** Para un repo **privado**, el plan gratis da solo **resúmenes de PR** (no revisión de código en el PR); la revisión real cuesta US$ 24–30/mes por desarrollador, **6–7× el costo total de hosting del plan (~4 US$/mes)**. Y lo que daría se superpone casi por completo con lo que ya tenés: Claude Code con `/code-review` (incluido `--comment` para publicar inline en el PR y `/security-review`), que además conoce `PLAN.md`, `DECISIONES.md` y los fixtures. Un solo desarrollador revisando sus propios PRs no necesita un segundo bot; el valor marginal sería una «segunda opinión» de otro modelo, que puede obtenerse ad hoc con la CLI gratuita (3 reviews/h, local, sin instalar nada en el repo) si alguna vez querés contrastar un cambio delicado (p. ej. el middleware de auth o el claim atómico del worker). No reemplaza nada del plan y no agrega cobertura (no corre tests, no mide reproducibilidad del motor).

**Riesgos:** - Gratis = resúmenes; el trial de 14 días vence y queda ruido de comentarios automáticos en cada PR.
- Permisos de GitHub App read/write sobre PRs y contenido de un repo que publica el binario del motor; otro tercero leyendo el código.
- Rate limits bajos en Free (1 PR/h) y 150 archivos por review: un PR grande de Fase 1 (scaffolding del monorepo) excede el límite.
- Si alguna vez se quiere, la vía barata es la CLI gratuita sobre el working tree, no la integración de PR.

## Linear — veredicto: quizás
**Qué es:** Gestor de issues/proyectos (teams, cycles, projects, roadmap) con app web/desktop/móvil, API GraphQL, webhooks, integración GitHub (enlaza PRs/commits por `ENG-123`, mueve issues a In Progress/Done con magic words, sync bidireccional con GitHub Issues) y un **MCP server oficial** (`https://mcp.linear.app/mcp`, Streamable HTTP, OAuth 2.1 con DCR, o `Authorization: Bearer <API key>`; endpoint `/mcp/readonly`). En este proyecto serviría para cargar las 8 fases del plan como projects/milestones y sus tareas como issues, y que Claude Code las cree/cierre vía MCP mientras implementa.

**Precio:** **Verificado en https://linear.app/pricing y https://linear.app/docs/billing-and-plans el 6/10/2026:** **Free:** US$ 0, «Unlimited members», **«250 issues»** (tope duro: «If you have over 250 issues, you will no longer be able to create new issues»), «2 teams», «10MB» por archivo, «15 pipelines» (releases), «API and webhook access», «Agent platform» y «Linear Agent» incluidos; todos los miembros son Admin. Integración GitHub sin restricción de plan para linking/magic words/sync (solo la creación de issues con IA y GitHub Enterprise Cloud están gateadas). **Basic:** US$ 10/usuario/mes (anual) → issues ilimitados, 5 teams, uploads ilimitados. **Business:** US$ 16/usuario/mes (anual) → teams ilimitados, guests, Asks, Insights. Enterprise: custom. **MCP (https://linear.app/docs/mcp, 6/10/2026):** `claude mcp add --transport http linear-server https://mcp.linear.app/mcp`; en Claude.ai/Desktop se agrega desde Settings > Connectors (disponible en Free/Pro de Claude); sin restricción de plan de Linear mencionada. No verifiqué si los issues cerrados/archivados cuentan para el tope de 250.

**Encaje:** Funciona y es gratis, y el MCP oficial permitiría literalmente «Claude Code, marcá M3.2 como hecha» desde la sesión; además tendrías la app móvil para mirar el backlog desde el celular. Pero para **una persona** no reemplaza nada y compite con dos opciones que ya están en la mesa a costo cero y sin cuenta nueva: (a) **`docs/TASKS.md` versionado** (lo que el plan ya hace con `PLAN.md`/`DECISIONES.md`; Claude Code lo edita en el mismo commit que el código; cero fricción, historial en git); (b) **GitHub Issues + Milestones por fase** en el mismo repo privado, ilimitados, con `gh` ya autenticado en tu PC (Claude Code los crea/cierra con `gh issue`), closing keywords en PRs idénticos a los de Linear, y el repo ya es el único sistema de registro. El **tope de 250 issues** es real para un plan de 8–9 semanas con 8 fases y subtareas granulares (el plan ya enumera >100 ítems entre criterios de aceptación, preguntas abiertas y riesgos); se puede esquivar siendo grueso, pero es una restricción que GitHub Issues no tiene. Recomendación: **TASKS.md por defecto**; GitHub Issues si querés tablero/móvil; Linear solo si ya lo usás y querés su UI — en ese caso usar `/mcp/readonly` desde Claude.ai y el `/mcp` completo solo en Claude Code.

**Riesgos:** - 250 issues en Free (no verifiqué si los Done/archived cuentan); al superarlo hay que pagar US$ 10/mes o podar.
- Otro sistema de registro fuera del repo: el estado de tareas deja de viajar con el código y los backups del plan (§3.9) no lo cubren; exportación manual.
- MCP con OAuth DCR y scopes de escritura: un conector más con permisos sobre tu workspace; preferir `readonly` donde alcance.
- Para un solo usuario, teams/cycles/projects son ceremonia; el beneficio real (app móvil, MCP) es cómodo pero no cambia el resultado del proyecto.
